# WorkPack 第一阶段迭代开发方案

日期：2026-11-08。状态：范围已确认，待实施。技术基础沿用 Electron、Vue、TypeScript、SQLite 和 Windows 本地文件存储。

## 1. 目标与范围

本期围绕项目资料交付增加五项能力：事项产出文件、Git 本地版本管理、文件库双视图、日期与紧急程度、Linear 项目和 issue 按需单向同步。

用户既能在 WorkPack 独立创建项目和事项，也能从 Linear 选择工作安排导入。每次提交填写版、签字版或盖章版都保留版本，产出文件可按项目、客户和事项集中查找。

文件内容与完成阶段由用户确认。本期范围不含自动识别签名盖章、自动填写模板、电子签章、Git 远程推送或双向同步。

## 2. 核心对象和使用流程

层级：项目 → 事项 → 文件项 → 产出文件 → 多个版本。

文件项继续承载模板来源、工作附件和待办。一份逻辑产出文件可多次上传，形成 V1、V2、V3；同一文件项也可增加多份不同产出，例如签收单和盖章回执。

1. 本地创建项目，或从 Linear 选择项目导入。
2. 本地创建事项，或勾选 Linear issue 导入为事项。
3. 为事项选择模板，生成独立工作副本和文件项。
4. 在文件项下新建产出文件，或为已有产出上传新版本。
5. 填写版本说明，勾选完成阶段，确认本次是否同时完成相关待办。
6. 应用保存文件并提交 Git，成功后显示新版本。
7. 从事项查看历史，或在文件库的产出视图集中筛选、下载。

## 3. 事项产出文件

### 3.1 页面与操作

事项抽屉中的文件项增加“产出文件”区域，保留现有工作附件和待办入口。产出列表显示名称、当前版本、阶段、最终版标记和更新时间。

| 操作 | 行为 |
| --- | --- |
| 新增产出 | 选择一个文件，填写名称、版本说明和阶段，建立 V1 |
| 上传新版本 | 保持产出 ID，保存新文件为下一版，允许 DOCX 转 PDF 等格式变化 |
| 查看历史 | 展示各版时间、说明、阶段、原始文件名和操作人 |
| 打开或导出 | 从指定版本提取原始字节，供系统程序打开或导出 |
| 设为最终版 | 明确指定某个版本为已确认的交付成果 |
| 使用历史版本 | 将历史内容另存为新版本，保留中间版本及恢复来源 |
| 移除产出 | 逻辑移除，可查看已移除记录；本期保留历史文件 |

版本号按每份产出独立递增。用户选择“上传新版本”才形成同一产出的后续版本，文件名相同不自动合并。

### 3.2 阶段、最终版和待办

- 阶段采用可多选标签：已填写、已签字、已盖章、已归档；未勾选时显示待处理。
- 阶段属于版本。V3 已盖章不回改 V1 的记录；新版本默认不继承上一版的确认阶段。
- 最终版是用户指定的版本指针，与签字、盖章标签分别记录。上传新版本不自动替换已指定最终版，界面提示当前版与最终版不同。
- 上传时可选择完成文件项中已有的相关待办。用户逐项确认，文件和版本保存成功后再更新待办。
- 待办与阶段分别存储。事后取消待办不篡改历史版本阶段；必要时在版本上追加更正记录。
- 阶段更正和最终版调整保留操作记录；文件内容始终不可原位改写。
- 普通“导出”使用当前版本；“导出最终版”明确使用最终版指向的版本。

## 4. Git 版本管理

### 4.1 仓库边界

采用一个项目一个本地受管 Git 仓库。建议存放在项目内专用目录 `.workpack/outputs-repo`，通过项目标记和项目 ID 识别。仓库只纳入 WorkPack 产出内容及版本元数据；模板原件、工作附件、SQLite 数据库和连接凭据继续由各自模块管理。

使用稳定 ID 作为受管路径，原始文件名作为元数据保存，避免项目改名、事项改期、同名文件和扩展名变化破坏版本关联。项目移动后更新根路径，历史版本仍按相对路径读取。

应用自动提交；界面使用“版本”“历史”“恢复为新版本”等词汇。Git 提交 SHA 作为技术定位信息保留在详情中。

### 4.2 文件与数据库一致性

SQLite 保存产出 ID、版本号、文件 SHA-256、Git 提交、Git 内路径和当前版指针；Git 保存文件内容及可重建索引的清单元数据。每次操作有唯一 operationId，并写入持久化操作日志。

保存顺序：校验并登记操作 → 临时目录复制和校验 → 写入本次受管路径及清单 → Git 提交 → 数据库事务登记版本、切换当前版及更新确认的待办 → 结清操作日志。

同一项目的写入串行执行。重复提交相同 operationId 返回同一结果，不产生重复版本。

启动时恢复未完成操作：Git 未提交的仅处理本操作暂存内容；Git 已提交而数据库未登记的根据 operationId 和清单补齐；数据库已登记的校验提交及文件哈希后结清。恢复失败时显示具体受影响产出，保留文件供重试。

首选由受管 Git 引擎提供接口，安装包携带固定版本运行时，避免依赖用户自行安装 Git。开发前完成最小验证，确认 Windows 原生打包、中文路径、大文件、二进制内容一致性及安装包体积，再锁定实现和许可证清单。

Git 调用位于主进程，以参数数组执行，固定工作目录和受管文件清单；隔离用户全局配置、hooks、过滤器及凭据配置，禁用交互式等待。历史提取按二进制流写入，不经文本编码转换。

### 4.3 文件安全与容量

- 新版本只增加历史记录。恢复和更正均追加记录，用户文件不会被历史操作直接覆盖。
- 现有附件不会自动宣称拥有历史。用户确认导入后，从当天建立首个版本，保留原附件和待办。
- 已有产出的事项、文件项和项目删除改为保留历史的逻辑移除；界面明确说明保留范围。物理清理作为后续独立功能。
- Git 缺失、仓库损坏、磁盘满和文件被占用时显示失败，不能显示版本保存成功或提前勾选待办。
- 二进制文件每次上传都可能增加仓库体积。原型阶段测量典型 Word、Excel、PDF 和扫描件，确定单文件上限、容量提醒及操作超时；形成可执行限制后进入正式开发。
- 上传完成形成快照。在外部程序修改导出件后，需要重新上传才形成新版本。
- 备份需同时包含数据库、模板、项目文件和受管 Git 历史。更改存储位置和跨电脑恢复验证必须覆盖这些新增目录；仅复制数据库不能恢复版本内容。

实现参考：[Git 提交文档](https://git-scm.com/docs/git-commit)、[Git 配置文档](https://git-scm.com/docs/git-config)。

## 5. 文件库双视图

文件库顶部增加“模板文件”和“产出文件”页签，各自保留筛选状态。

模板视图沿用分类、导入、导出和模板编辑。产出视图直接查询事项中的产出索引，同一产出不复制成另一份业务记录。

| 项目 | 一期设计 |
| --- | --- |
| 默认列表 | 每份产出显示当前版，不展开全部历史 |
| 列 | 名称、项目、客户、事项、阶段、版本、最终版标记、更新时间 |
| 搜索 | 产出名、原始文件名、项目名、事项名及客户名 |
| 筛选 | 项目、客户、事项、阶段、存在最终版、更新时间范围 |
| 分组 | 不分组、按项目、按客户、按事项，切换时不改变归属 |
| 操作 | 打开、导出、版本历史、进入所属事项 |
| 批量导出 | 支持当前版或最终版；同名自动避让，缺失项明确列出 |
| 已移除 | 单独入口查看，默认列表隐藏 |

导出文件采用用户能识别的名称，携带项目、事项及版本号；输出前预览范围。历史查询从指定 Git 提交读取，数据库列表查询分页执行，不逐行扫描全部仓库。

## 6. 日期和紧急程度

| 层级 | 新增字段 | 默认与规则 |
| --- | --- | --- |
| 项目 | 计划开始日期、目标完成日期、紧急程度 | 日期可空，紧急程度默认未设置 |
| 事项 | 保留业务日期，新增资料截止日期、紧急程度 | 业务日期沿用本地日历；截止日期可空；紧急程度默认继承项目 |
| 产出版本 | 上传时间 | 自动记录，不代替业务日期 |

紧急程度取值为未设置、低、普通、高、紧急。事项可改为独立等级，也可恢复继承；展示时标注继承来源。

纯日期按日历日期保存，不转换为 UTC 时间戳；上传和同步时间按时间戳保存并按本地时区显示。截止日期当天不算逾期，次日仍有资料缺口才算逾期；已完成事项不再显示逾期。

工作台、项目列表和事项列表显示紧急程度、截止日期及逾期标记，支持按截止日期和紧急程度排序。逾期不自动修改紧急程度。项目和事项默认均可不设日期，不以占位日期补齐。

## 7. Linear 按需单向同步

### 7.1 连接与导入流程

设置增加可选 Linear 连接。应用通过独立授权连接读取 Linear 数据，Codex 已连接的插件不等于 WorkPack 已取得授权。第一版支持用户主动同步，自动定时同步后续评估。

流程：连接并确认工作空间 → 选择项目 → 预览字段及客户关联 → 新建或关联本地项目 → 勾选 issue → 导入为事项 → 按需再次同步并查看结果。

授权优先采用官方 OAuth 的只读范围；个人内部试用可评估只读 API key 模式。凭据由操作系统凭据能力保护，主进程使用，不能进入 SQLite 业务导出、日志或 Git。断开连接后本地项目和产出仍可使用。

同步只读取 Linear，本期不向 Linear 创建、修改或删除项目、issue、评论及附件。业务范围中的签字、盖章、待办和产出版本均在 WorkPack 管理。

### 7.2 字段映射

| 来源 | WorkPack | 默认规则 |
| --- | --- | --- |
| Linear workspace ID、项目 ID、issue ID 和链接 | 外部关联 | 使用稳定 ID 去重，不能靠同名判断重复 |
| 项目名称及说明 | 项目名称及来源说明 | 导入时预填；后续改名不直接重命名磁盘目录 |
| 项目 lead | 项目负责人 | 保存来源用户 ID 和显示名称，本地身份由用户确认 |
| 项目 startDate、targetDate | 计划开始日期、目标完成日期 | 保留来源精度；月度、季度日期不能伪造为某一天 |
| 项目 priority | 项目紧急程度 | 按对应语义映射，未设置保留未设置 |
| 客户及 customer request 关联 | 客户档案及项目客户 | 预览确认；存在多个客户时手动选择本项目主客户 |
| issue 标题、描述、assignee | 事项名称、来源说明、经办人 | 仅处理用户勾选的 issue |
| issue dueDate | 资料截止日期 | 不覆盖事项业务日期 |
| issue priority | 事项独立紧急程度 | 无来源优先级时默认继承项目 |
| Linear 项目和 issue 状态 | 来源状态 | 仅展示，不自动勾选资料待办或判定归档 |

客户关系不能由名称、域名或描述猜测。Linear 可读的客户资料进入本地候选列表，项目和客户关系由明确的来源关联及用户确认建立；未提供的联系人、电话等信息由本地补充。

导入 issue 只建立事项信息。文件模板、工作附件和产出由用户在 WorkPack 中选择或上传，issue 附件和评论不随首版同步自动下载。

### 7.3 更新、冲突和异常

- 每个字段记录来源、最近同步值和本地覆盖标记。默认跟随来源；用户本地修改同步字段时选择保留本地值，后续同步不覆盖。
- “恢复跟随 Linear”提供新旧值预览，用户确认后更新。WorkPack 专有字段始终由本地维护。
- 外部关联以 provider、workspace ID、对象类型和 external ID 建立唯一约束。重复同步更新原记录；重名的现有本地项目由用户显式关联。
- issue 转移到另一个项目时提示归属变化，用户确认后调整事项关系和文件路径；一期可先保留原归属并标记待处理。
- 来源归档、删除或无权限访问时保留本地记录与文件，分别显示已归档、已删除或暂不可访问，不将一次缺失响应当作删除。
- 同步过程中分页处理，按对象保存结果和游标，失败可重试；不能把部分成功当成全部成功。
- 同步结果显示新增、更新、本地保留、跳过和失败数量及具体对象。历史错误不阻止其他本地功能。
- 断开连接停止同步并清除凭据；保留已导入信息及来源标记，允许重新连接同一工作空间。

接口依据：[Linear GraphQL](https://linear.app/developers/graphql)、[OAuth 授权](https://linear.app/developers/oauth-2-0-authentication)。客户与项目关系通过开发前接口样本验证后锁定，未取得的数据保留为空。

## 8. 数据模型与模块

建议以向后兼容迁移扩展当前 workpack-v3.sqlite；物理文件名是否调整在实施时统一，不能以换文件名的方式绕过旧数据迁移。

| 数据对象 | 关键内容 |
| --- | --- |
| 项目和事项扩展 | 计划日期、截止日期、紧急程度、事项继承标记 |
| customers | 本地客户 ID、名称及本地补充资料，项目关联客户 ID |
| outputs | 所属文件项、产出名称、当前版本、最终版本、逻辑移除时间 |
| output_versions | 产出 ID、顺序号、原名、大小、哈希、阶段、说明、操作人、提交及受管路径 |
| output_operations | operationId、执行阶段、恢复信息、错误及时间 |
| output_audit | 阶段更正、最终版指定及逻辑移除记录 |
| external_links | 工作空间、外部对象 ID、本地对象、来源快照和字段覆盖标记 |
| sync_runs | 同步范围、分页游标、每个对象结果及最近成功时间 |

为产出归属、更新时间、项目客户、外部唯一 ID 和版本序号建立对应索引和约束。旧项目客户字符串迁移为客户候选，重名不自动合并，保留原值供确认。

主进程新增产出服务、Git 适配层及 Linear 只读适配层；复用当前 IPC 校验和存储模块。渲染进程通过固定接口上传、读取历史和发起同步，不直接访问文件系统、Git 或凭据。界面实现遵循 [DESIGN.md](../../../../DESIGN.md)。

| 顺序 | 交付内容 | 进入下一步的条件 |

| M1 数据基础 | 兼容迁移、日期、紧急程度、产出表和外部关联表 | 旧数据读取、回滚及日期边界测试通过 |
| M2 产出和历史 | 上传、新版本、Git 提交、历史读取、最终版、故障恢复 | 同项目串行、幂等和重启恢复通过 |
| M3 文件库双视图 | 查询、分组、筛选、历史入口和批量导出 | 事项与文件库显示一致，导出内容一致 |
| M4 Linear 项目导入 | 可选连接、客户确认、项目关联和字段更新 | 无重复记录、本地覆盖保留、断网可用 |
| M5 issue 导入 | 勾选导入事项、手动更新、转移和归档提示 | 与文件模板和产出流程串联通过 |

Git 技术验证和 Linear 字段验证可独立开展；产出文件功能不依赖 Linear 连接。本期按里程碑拆分提交，开发进展对应 Linear issue 时写入评论，描述区维护背景及验收标准。

## 10. 验收标准

1. 同一事项上传三版签收单，历史均可下载，字节哈希与上传原件一致；另一事项版本独立。
2. 新版本支持原始格式变化，签字和盖章可同时标记；阶段、待办和最终版互不误改。
3. 恢复 V1 形成新的 V4，V2、V3 仍可查；最终版下载准确。
4. 上传、Git 提交或数据库保存各阶段中断后重启，可恢复或明确重试；不出现虚假成功或重复版本。
5. 项目移动、重命名及事项改期后仍可读取所有版本；逻辑删除保留历史。
6. 文件库切换双视图，按项目、客户和事项筛选分组，结果与事项内一致，批量导出无静默覆盖。
7. 日期可空，本地午夜和跨年不偏移；逾期、紧急程度及继承显示和排序准确。
8. 首次导入 Linear 项目和选定 issue 后再次同步，不重复建项目和事项；未选 issue 不导入。
9. 本地覆盖字段得到保留，恢复跟随有预览；来源完成不自动标记资料已签字或归档。
10. Linear 断网、权限失效、分页失败、归档和转移均有明确结果，已有资料及本地功能可用。
11. 未连接 Linear 的用户能完成同样的产出与版本管理流程；请求及日志无远程写入和凭据泄漏。
